# Epic 5 — 目錄與頁碼：規格 (Spec)

這是實作 `epic-5-toc-pagination` 的唯一事實來源。決策的完整討論過程與理由請見 `design.md`（`/grill-with-docs` 2026-07-14，15 項決策）。本文件延續 `design.md` 的所有範圍界定，不重複列出理由，僅在此定案核心介面/型別，供 Scrum Master 階段拆解工單使用。

## Problem Statement

使用者在閱讀較長的 EPUB／PDF 書籍時，目前完全沒有辦法：

- 快速瀏覽整本書的章節結構並跳轉到任一章節（無目錄功能）。
- 知道自己讀到全書的第幾頁／還剩多少（無頁碼顯示）。
- 直接輸入或拖曳跳到指定頁碼（無跳頁功能）。
- 在閱讀畫面上看到目前所在章節與進度（無頁首／頁尾）。
- 關閉 App 後下次開啟同一本書，自動接續上次讀到的地方——目前每次開書都固定從頭開始，即使前一分鐘才讀過。

這些缺口讓長書閱讀體驗明顯低於一般電子書閱讀器的基本水準，且與本專案「單機閱讀優先」的當前開發主軸（見 `docs/epics.md` 開發順序決議）直接相關——這些都是不需要雲端／帳號即可完整交付的核心閱讀體驗。

## Solution

在既有的 `ReaderScreen` 統一入口之上，為流式 EPUB 與 PDF 兩種格式新增：

1. 一個可展開／收起的層級目錄清單（EPUB 專屬，PDF 因平台 API 限制不支援），每項顯示標題與估算／精確頁碼，點擊可於 200ms 內跳轉。
2. 頁碼顯示與跳頁能力：PDF 沿用既有精確頁碼機制；EPUB 因 Readium 無螢幕感知分頁 API，改用字元啟鞍法估算「目前頁碼／總頁數」。跳頁 UI 為輸入框＋滑桿雙向同步。
3. 可獨立開關的頁首（章節名稱＋目錄入口，取代現有 AppBar）與頁尾（進度＋頁碼＋跳頁控制項），僅適用流式 EPUB／PDF，不適用固定版面漫畫。
4. 本機（不需帳號／網路）閱讀位置記憶：離開閱讀畫面或 App 進入背景時，自動把目前位置寫入本機資料庫；下次開啟同一本書自動跳回去。此為本 epic 主動擴大的範圍（超出 PRD FR 逐字要求），因為沒有它，頁碼／跳頁功能在「每次開書都回到第一頁」的前提下體驗會很奇怪。

PDF 內建大綱／書籤的目錄提取因平台 API 限制不在本 epic 範圍內，另立後續工單。

## User Stories

1. 作為一個正在閱讀長篇 EPUB 小說的讀者，我想要看到整本書的章節目錄，這樣我可以快速了解全書結構。
2. 作為一個正在閱讀長篇 EPUB 小說的讀者，我想要點擊目錄裡的任一章節就跳過去，這樣我不用一頁一頁往後翻。
3. 作為一個正在閱讀有子章節的 EPUB 教科書的讀者，我想要目錄能顯示多層級結構（章→節），這樣我可以精確找到我要的段落，而不是只看到一堆扁平的章節標題。
4. 作為一個正在閱讀 EPUB 的讀者，我想要目錄清單能標示我目前在哪一章，這樣我不用另外去猜自己讀到哪。
5. 作為一個正在閱讀 EPUB 或 PDF 的讀者，我想要看到「目前頁碼／總頁數」，這樣我可以掌握閱讀進度與剩餘篇幅。
6. 作為一個正在閱讀 PDF 的讀者，我想要看到的頁碼是精確值（不是估算），因為 PDF 本身就是固定分頁格式。
7. 作為一個正在閱讀 EPUB 的讀者，我能接受頁碼是模擬估算值（非逐字精確），只要大致反映我讀到全書的哪個位置。
8. 作為一個正在閱讀 EPUB 或 PDF 的讀者，我想要直接輸入頁碼跳過去，這樣我可以精確跳到某一頁（例如老師交代要看第 87 頁）。
9. 作為一個正在閱讀 EPUB 或 PDF 的讀者，我想要用拖曳滑桿的方式快速瀏覽跳頁，這樣我可以用手感直覺地瀏覽全書進度而不用打數字。
10. 作為一個正在閱讀 EPUB 或 PDF 的讀者，我想要拖曳滑桿與輸入框的數字保持同步，這樣我操作其中一個時不會看到另一個顯示過期或矛盾的數字。
11. 作為一個正在閱讀 EPUB 或 PDF 的讀者，我想要能開啟或關閉頁首（顯示章節名稱與目錄入口），這樣我可以依自己喜好決定畫面上要不要出現這個資訊列。
12. 作為一個正在閱讀 EPUB 或 PDF 的讀者，我想要能開啟或關閉頁尾（顯示進度與頁碼），這樣我可以在想要沉浸閱讀時把這些資訊隱藏起來。
13. 作為一個正在閱讀 EPUB 或 PDF 的讀者，我希望頁首與頁尾的顯示/隱藏是各自獨立的開關，這樣我可以只留頁尾不留頁首（或反過來），而不是綁在同一個開關上。
14. 作為一個正在閱讀 EPUB 的讀者，我想要點擊頁首上的章節名稱就能展開完整目錄，這樣我不用另外找目錄按鈕在哪。
15. 作為一個正在閱讀漫畫（固定版面 EPUB）的讀者，我不會看到頁首/頁尾疊加在既有的沉浸式閱讀控制項上，這樣既有的翻頁熱區與浮動按鈕不會被新元件擋住或搞亂版面。
16. 作為一個正在閱讀 PDF 的讀者，我不會看到「目錄」入口按鈕，因為目前 PDF 沒有目錄功能——我希望這個入口乾脆不要出現，而不是點進去看到一個空白或錯誤畫面。
17. 作為一個正在閱讀書籍的讀者，我想要關閉 App（或切到背景）後，下次重新開啟同一本書時自動回到我上次讀到的地方，這樣我不用每次都重新找位置。
18. 作為一個正在閱讀書籍的讀者，我不需要登入帳號或連上網路，這個「記住上次讀到哪」的功能就要能運作，因為這是單機、不涉及雲端同步的基礎能力。
19. 作為一個正在調整字體大小或行距的讀者，我想要頁碼顯示能反映我目前的排版設定（而不是用舊的字體大小算出來的過期頁碼），這樣頁碼資訊才有參考價值。
20. 作為一個正在閱讀 EPUB 的讀者，我想要目錄清單上每個項目除了標題，也能看到大概的頁碼，這樣我可以評估這一章有多長、離我目前位置有多遠。
21. 作為維護此專案的工程師，我想要既有一直沒被呼叫過的 `onPageChanged` 死程式碼被清理或替換掉，這樣未來的人不會誤以為它是有效的頁碼回報機制。
22. 作為維護此專案的工程師，我想要「閱讀位置」與「顯示偏好設定」存在不同的資料表／欄位群組，這樣兩種本質不同（系統追蹤的狀態 vs. 使用者主動選擇）的資料不會混在一起難以維護。

## Implementation Decisions

### 範圍界定（承接 `design.md`，不重複展開理由）

- 目錄（TOC）僅支援流式 EPUB；PDF 因 `PdfRenderer` 平台 API 無法讀取內建大綱／書籤而不支援，另立後續工單評估。
- FR-12（TXT 自動章節解析）不在本 epic 範圍，延後至 `epic-11-txt-engine`。
- 頁首／頁尾（FR-40）僅適用流式 EPUB 與 PDF，不適用固定版面（FXL 漫畫）。
- 雲端進度同步／衝突偵測不在本 epic 範圍，屬 `epic-8-sync`；本 epic 僅建立本機基礎設施供其擴充。

### 目錄模組

- 資料來源：Readium `Publication` 的目錄樹狀結構，於原生端一次性讀取後序列化傳給 Dart 端，保留完整巢狀階層（不攤平）。
- Dart 端以可展開／收起的層級樹狀清單呈現，比照專案既有 Bottom Sheet 慣例開啟（與 `PdfSettingsSheet`／`ReaderSettingsSheet`／`FxlSettingsSheet` 一致的開啟方式），透過 `ReaderScreen` 觸發。
- 每個目錄項目顯示標題與估算頁碼（沿用下方「分頁估算模組」的換算邏輯）。
- 當前章節所屬層級預設展開，其餘收起；當前章節項目需視覺高亮。
- 點選項目後，透過 Readium 既有的定位機制（Locator）導航，須於 200ms 內完成跳轉。
- PDF 格式下，目錄入口完全不顯示（非顯示後空狀態）。

### 分頁估算模組（EPUB 專屬）

- 採用字元／字數區間啟鞍法：原生端提供全書字元數（一次性計算，讀取整本書內容長度後回傳，非逐次即時計算）；Dart 端依目前生效的版面參數（字體大小、行距、段落間距、邊距、排版方向）估算「每螢幕可容納字元數」，換算出估計總頁數。
- 目前頁碼由 Readium 提供的全書閱讀進度比例換算而得（比例 × 估計總頁數，四捨五入）。
- 估計總頁數與目前頁碼須在任一版面參數變動時立即重新計算，維持與實際排版狀態一致。
- 明確聲明此為模擬估算值，非逐頁精確值——與 PRD 對 EPUB 分頁「模擬」的定性一致，不追求與底層渲染引擎逐頁對齊。
- 既有的、從未被實際觸發過的分頁回報死程式碼（EPUB 讀取端一個永遠不會被呼叫的分頁監聽覆寫方法）須在本 epic 內清理或替換為本模組的正式機制，避免死程式碼與新機制並存造成混淆。

### PDF 頁碼

- 沿用既有精確頁碼基礎設施（目前頁索引／總頁數皆已存在），不需要估算邏輯，直接顯示與供跳頁使用。

### 跳頁互動

- UI 提供輸入框與滑桿兩種輸入方式，兩者雙向同步：拖曳滑桿即時更新輸入框顯示的數字，輸入框確認輸入後同步更新滑桿位置；任一方觸發最終跳頁動作。
- EPUB 與 PDF 共用同一套跳頁 UI 元件，差別僅在於「總頁數」是估算值還是精確值。

### 頁首／頁尾

- 頁首開啟時取代現有的 App 頂部標題列——標題區改為顯示目前章節名稱（可點擊展開目錄），既有的版面設定入口維持可用；頁首關閉時回到現行的靜態標題列。
- 頁尾為獨立於頁首的顯示元件，開啟時顯示閱讀進度（百分比）與目前頁碼／總頁數，並整合跳頁輸入框／滑桿。
- 頁首與頁尾的顯示/隱藏各自獨立控制，且為單書持久化設定（比照既有版面偏好設定的持久化模式），預設皆為顯示。

### 本機閱讀位置記憶

- 新增的位置資料（EPUB 用序列化後的 Readium 定位資訊；PDF 用頁索引）存放於書籍本身的資料模型（`Book`），而非既有的版面偏好設定資料模型（`BookReaderPrefs`）——理由：閱讀位置是系統依使用者行為持續追蹤更新的「狀態」，與 `BookReaderPrefs` 既有欄位所代表的「使用者主動選擇的顯示設定」在資料語意上不同類，不應混在同一張表／同一組欄位裡維護。
- 既有的、長期恆為 0（從未被寫入過）的書籍進度百分比欄位，本 epic 內須正式活化（真正依讀取到的位置回填），與新增的精確定位欄位（EPUB 用定位字串、PDF 用頁索引）一併寫入。
- 寫入時機：使用者離開閱讀畫面時，以及 App 進入背景時，各觸發一次寫入；刻意不逐次翻頁／捲動即時寫入，避免捲動翻頁模式下高頻率資料庫寫入。
- 讀取時機：開啟書籍時，若存在既有位置資料，原生端須以此為起始位置渲染（而非固定從頭開始）。
- 此為單書本機資料，不涉及帳號或雲端請求；`epic-8-sync` 未來可在此基礎上疊加雲端同步與衝突偵測，不需重新設計本機資料結構。

## Testing Decisions

- **接縫沿用既有 `ReaderScreen` 單一入口**，不新增測試接縫——與專案 `CLAUDE.md` 明訂的「`ReaderScreen` 是唯一的閱讀器 seam」一致（已與使用者確認）。
- 測試分兩層，比照專案既有慣例：
  - **`app/test/`**（純 widget test，不需真機）：驗證格式偵測後正確分派、目錄清單的展開/收起互動與跳轉呼叫、頁首/頁尾顯示/隱藏開關邏輯、跳頁輸入框/滑桿的雙向同步邏輯、分頁估算在版面參數變動時是否觸發重算——皆可用既有的 `WidgetTester` 模式驗證，不涉及原生渲染結果本身。
  - **`app/integration_test/`**（真機）：驗證真正的目錄跳轉在 200ms 內完成、EPUB 頁碼估算與 PDF 精確頁碼在真實書籍上顯示合理、開書後自動跳回上次位置的端到端流程（開書 → 翻頁/跳頁 → 離開/背景 → 重開 → 斷言起始位置與離開前一致）。
- 良好測試的判準（比照專案既有測試撰寫慣例，非本 epic 新創）：只驗證外部可觀察行為（畫面上出現的元件、`ReaderScreen` 對外暴露的 Key、資料庫最終寫入的值），不斷言內部實作細節（例如不直接斷言 Dart 端某個私有欄位的中間計算值，除非該值本身就是測試想驗證的最終結果）。
- 既有的先例（`app/test/screens/reader_screen_test.dart`、`app/integration_test/reader_screen_test.dart`）已建立這種「透過 `ReaderScreen` 公開行為斷言」的測試風格，本 epic 延續，不另立新風格。
- 目錄與分頁估算邏輯屬於純 Dart／純 Kotlin 的可獨立驗證邏輯（無需真實裝置渲染），應優先以純邏輯單元測試涵蓋（比照專案既有的原生端 JVM 單元測試慣例，例如 `PdfImageProcessor`／`EpubFxlScaler` 的既有先例），只有真正涉及原生渲染或真機互動的部分才需要 `integration_test`。

## Out of Scope

- PDF 目錄提取——平台 API 限制，另立後續工單評估自訂解析器或第三方函式庫。
- TXT 目錄與分頁（FR-12）——留待 `epic-11-txt-engine`。
- 固定版面（FXL 漫畫）的頁首／頁尾——與 `epic-16-dual-page` 既有的浮動控制系統衝突，維持現狀不變。
- 雲端進度同步、衝突偵測——`epic-8-sync` 職責。
- 目錄項目／頁碼估算的逐頁精確度保證——僅為模擬估算，非像素或逐頁精確對齊底層渲染結果。
- 頁首／頁尾內容以外的版面客製化（例如頁首/頁尾的顏色、字型另外調整）——沿用既有主題與版面設定，不新增獨立樣式系統。

## Further Notes

- 全書字元數的計算成本與快取策略（是否需要背景執行緒、是否需要快取避免重複計算）留待 Scrum Master 拆解工單時決定，非本規格需要定案的介面問題。
- 目錄項目跳轉所需的底層定位轉換機制（如何把目錄項目的連結轉換成可供原生導航使用的定位物件）屬於實作細節，留待對應工單的實作計畫決定。
- 本機位置寫入非 100% 保證不遺失（App 被系統強制終止的極端情況仍有極小機率遺失最後一次進度）——此為已知、可接受的殘留風險，不在本 epic 內追求同步阻塞寫入等更強保證機制，比照專案既有「已知限制」誠實揭露慣例。
- 本規格未列出具體檔案路徑或程式碼片段（依 `/to-spec` 慣例），實作前請參閱 `design.md`「架構影響摘要」表格了解受影響模組的對應關係，實際簽章與型別定義留待 Scrum Master／實作計畫階段決定。
