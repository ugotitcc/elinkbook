# Epic 24 — PDF 渲染引擎重建（遷移至 pdfrx/PDFium）：Spec

> 本文件為本 Epic 的唯一事實來源，取代 `design.md` 對應章節的暫定內容。決策依據見 `design.md`（Discovery）與 `docs/adr/0022-pdf-engine-migrate-to-pdfrx.md`。

## Problem Statement

elinkBook 的 PDF 閱讀體驗，目前受限於底層渲染引擎（Android `PdfRenderer` 原生 API）的能力邊界，比書架上其他格式（EPUB）少了三項核心閱讀功能：無法瀏覽書籍目錄（PDF 內建的大綱/書籤樹完全讀不到）、無法在書中搜尋文字、無法用縮圖快速瀏覽/跳頁。雙頁並列閱讀雖然存在，但底層完全靠自行拼接點陣圖實現，脆弱且難以維護。使用者想在單一書本內快速找到某個章節或某段內容時，PDF 是三種格式中唯一做不到的一種。

## Solution

把 PDF 渲染引擎從平台原生 `PdfRenderer` 完全遷移至 `pdfrx`（Google PDFium 透過 `dart:ffi` 直接呼叫，非透過 `PlatformView`），一次性補齊目錄瀏覽、內文搜尋、頁碼縮圖三項現有格式沒有的能力，同時保留雙頁並列、書籤、劃線標註、E-Ink 影像濾鏡等既有能力於功能對等的前提下遷移過去。PDF 的閱讀工具列一併改為與 EPUB 一致的浮動圓形按鈕（FAB）呈現，讓三種格式的操作邏輯與視覺語言收斂一致。

## User Stories

1. As a PDF 讀者, I want 開啟 PDF 書籍時能看到書籍內建的章節目錄, so that 我可以像讀 EPUB 一樣快速跳到想看的章節，不必一頁一頁翻找。
2. As a PDF 讀者, I want 目錄項目點擊後直接跳轉到對應頁面, so that 導覽不需要額外操作或等待。
3. As a PDF 讀者, I want 目錄樹狀結構能正確顯示巢狀章節層級, so that 我能理解書籍的組織架構，不只是一份平面清單。
4. As a PDF 讀者, I want 在已開啟的書籍內搜尋文字, so that 我能快速找到記得的某段內容，不必憑記憶翻找頁碼。
5. As a PDF 讀者, I want 搜尋結果以高亮方式標示在頁面上, so that 我能一眼看到符合的文字在哪裡。
6. As a PDF 讀者, I want 搜尋結果可以逐一跳轉瀏覽, so that 同一個關鍵字出現多次時我能依序檢視每一處。
7. As a PDF 讀者, I want 用頁碼縮圖快速瀏覽整本書, so that 我能透過視覺記憶（例如某頁有張圖）快速定位，而不是只能看數字頁碼。
8. As a PDF 讀者, I want 橫向閱讀時可以雙頁並列顯示, so that 大螢幕/平板閱讀體驗更接近實體書。
9. As a PDF 讀者, I want 雙頁模式的「自動/永遠雙頁/永遠單頁」三態設定與 EPUB FXL 的既有邏輯一致, so that 我在不同格式書籍間切換時不需要重新學習。
10. As a PDF 讀者, I want 已加入書籤的頁面可以快速標記與移除, so that 我能標記重要頁面而不需要另外記錄頁碼。
11. As a PDF 讀者, I want 選取頁面範圍加上劃線與備註, so that 我能像紙本書一樣標註重點，並保留原有跨模式（雙頁/單頁切換）下的一致視覺。
12. As a PDF 讀者, I want 我劃線/加書籤時能精準對應到我實際選取的區域, so that 之後回顧時不會找錯位置。
13. As E-Ink 裝置使用者, I want PDF 頁面仍支援對比度/亮度調整, so that 在低對比度掃描件上文字更容易閱讀。
14. As E-Ink 裝置使用者, I want PDF 加粗（型態學膨脹）濾鏡仍然可用, so that 淡色掃描件的筆畫在墨水屏上更清楚。
15. As E-Ink 裝置使用者, I want 智慧自動裁切與手動選區裁切仍然可用, so that 我能去除頁面白邊、讓內容佔滿可視區域。
16. As E-Ink 裝置使用者, I want 這些影像處理運算不會讓翻頁/操作介面卡頓, so that 閱讀體驗不因為新引擎變差。
17. As PDF 讀者, I want 頂部工具列改用跟 EPUB 一樣的浮動圓形按鈕, so that 我在兩種格式間切換操作習慣一致。
18. As PDF 讀者, I want 返回/目錄/版面設定/書籤/筆記/進度-跳頁 六個按鈕都能在閱讀畫面直接操作, so that 我不需要多層選單就能完成常用操作。
19. As PDF 讀者, I want 這些浮動按鈕跟隨我目前選用的主題（深色/淺色/羊皮紙）配色, so that 視覺風格與其他畫面一致，且在電子紙裝置上仍清楚可辨識。
20. As PDF 讀者, I want 頁面導覽（目前頁/總頁數、跳頁）改成點擊按鈕才彈出，不常駐佔用畫面, so that 可視閱讀區域比現在更大。
21. As 擁有邏輯頁碼標籤的 PDF（例如封面用羅馬數字）讀者, I want 看到書籍原本的頁碼標籤, so that 頁碼顯示與紙本印刷一致；同時 As 該讀者, I want 跳頁功能仍然可靠, so that 邏輯頁碼標籤不是數字或不連續時不會導致跳轉錯誤。
22. As 從 SAF（系統檔案選擇器）匯入 PDF 的使用者, I want 我的書籍不會因為新引擎而佔用雙倍儲存空間, so that 匯入大型 PDF 不會不必要地消耗裝置儲存。
23. As 擁有 100MB 以上大型掃描 PDF 的使用者, I want 開書速度維持在可接受範圍（目標 2 秒內）, so that 大檔案不會讓我每次打開都要長時間等待。
24. As 開發者/未來維護者, I want 新的 PDF 渲染邏輯能直接用 `flutter test` 對真實 PDF 檔案驗證, so that 迴歸測試不必依賴真機/模擬器就能在 CI 跑。
25. As 掃描件（純圖片、無文字層）PDF 讀者, I want 即使書籍沒有可抽取的文字層，劃線/選取功能仍然可用, so that 老舊掃描書籍不會因為新引擎而失去標註能力。

## Implementation Decisions

### 引擎替換範圍

- 現行原生 `PdfRenderer` 為底層的 PDF 渲染模組（含對應的原生端影像處理模組）與其對外暴露的 method channel 契約全部退場，改由新的、以 `pdfrx` 為底層的 Dart 端 PDF 閱讀 widget 取代，直接在 Flutter widget 樹中渲染，不再透過 `PlatformView`。
- `ReaderScreen`（唯一閱讀器 seam）對外可觀察行為（`filePath`／`bookId`／`prefsRepository`／`bookTitle` 建構參數，`Key('reader_loading_indicator')`／`Key('reader_error_text')` 狀態暴露）維持不變——這是格式無關的既有契約，PDF 引擎替換屬於 `ReaderScreen` 內部實作細節。
- 新 PDF 閱讀 widget 對外的建構參數（檔案路徑、開書成功/失敗回呼）維持與現行契約語意相容（開書成功一次性回呼、開書失敗攜帶錯誤訊息），讓 `ReaderScreen` 既有的 `_state`（`loading`/`rendered`/`error`）狀態機與 Issue 33/`/diagnose` 建立的「只在 loading 時才轉為錯誤畫面」既有守衛邏輯不需要改動。

### 目錄（TOC）

- 新增一個格式無關的目錄項目抽象介面（暫名 `BookTocItem`：標題、定位點、子項清單、巢狀層級），EPUB 既有的目錄 Bottom Sheet UI 元件改為消費這個抽象介面，而非直接依賴 EPUB 專屬的目錄項目型別；PDF 端把 `pdfrx` 的大綱解析結果（標題、目的頁碼、子項層級）轉換為同一介面的實例。
- PDF 目錄項目點擊後的行為（跳轉、目前所在章節高亮、巢狀展開狀態）與 EPUB 既有目錄 Bottom Sheet 行為一致。
- 目錄按鈕的啟用時機比照 EPUB 既有慣例：書籍尚未成功開啟、或目錄背景載入尚未完成前停用，避免使用者在資料就緒前點擊開啟空白清單。

### 頁面導覽（頁碼、頁碼縮圖、跳頁）

- 頁碼顯示採雙顯示模式：若 PDF 提供邏輯頁碼標籤（Page Label，例如封面羅馬數字），與實體頁碼/總頁數並列顯示（例如「iii (3/150)」）；若無邏輯頁碼標籤，回退為現行純數字頁碼顯示。跳頁/進度換算邏輯一律以絕對 0-indexed 頁碼為運算基準，不依賴頁碼標籤格式，避免頁碼標籤非數字或不連續時跳頁錯誤。
- 頁碼縮圖為新增功能：以頁碼列表/格狀呈現整本書每一頁的縮小預覽圖，點擊縮圖跳轉至對應頁面；縮圖產生方式須避免一次性渲染全書縮圖造成的效能/記憶體問題（例如可視範圍內才產生、或有上限的快取策略），具體策略留給實作階段依真機效能驗證決定，不在本文件預先鎖定演算法細節。滑出可視範圍外而被快取淘汰的縮圖影像資源須明確釋放（`dispose()`），避免大量頁數書籍快速捲動縮圖面板時發生記憶體洩漏（`/superpowers:receiving-code-review` 審查回應）。
- 現行「頁面導覽」（目前頁/總頁數/跳頁）從常駐於畫面底部的既有元件，改為浮動「進度/跳頁」按鈕觸發的 Bottom Sheet 呈現，不再擠壓可視閱讀區域高度，行為比照 EPUB 既有的對應機制。

### 雙頁並列

- 沿用既有的「雙頁模式（Dual-Page Mode）」三態設計（自動/永遠雙頁/永遠單頁，`CONTEXT.md` 既有詞彙，單書持久化於既有偏好設定），語意與資料層不變，僅底層改由 `pdfrx` 的原生雙頁排版能力實作，取代現行自行拼接點陣圖的作法。
- 雙頁配對規則（封面獨立顯示、之後兩兩配對）與既有「Spread（跨頁）」既有詞彙定義一致。

### 內文搜尋

- 搜尋範圍限定單一已開啟 PDF 文件內（in-document search），與全書庫全文檢索（FTS5，`docs/epics.md` Backlog，尚未開始）是不同功能，兩者互不依賴、不整合。
- 搜尋結果須支援：以高亮標示所有符合位置、可逐一跳轉至下一個/上一個符合結果。
- 掃描件（無文字層）PDF 無法搜尋到內容——這是 PDF 格式本身的限制（沒有文字層可供比對），非本次實作缺陷，UI 上須有合理的空結果呈現（而非誤導使用者以為搜尋功能故障）。

### 劃線/備註/選取機制

- **保留現行「長按拖曳框選矩形」的選取互動模式作為主要機制**，不改為純文字選取——理由：現行選取以頁面座標（相對頁面內容範圍的百分比矩形）為資料模型，不依賴 PDF 是否有可抽取的文字層，對掃描件（純圖片）PDF 與一般數位原生 PDF 都能一致運作；若改為完全依賴 PDFium 文字定位 API 的文字選取，掃描件 PDF 會直接失去劃線能力，是真實的功能倒退（見 User Story 25）。
- 選取範圍的資料模型（頁碼＋相對頁面內容範圍的百分比矩形＋相對整個 widget 尺寸的百分比矩形，用於浮動工具列定位）維持現行語意不變，僅底層渲染來源改變。**雙頁模式下，「相對頁面內容範圍的百分比矩形」須明確定義為相對單一頁面本身的邊界，不是相對包含左右兩頁的整個雙頁 viewport**（`/superpowers:receiving-code-review` 審查回應）——否則單頁/雙頁模式切換（或雙頁模式下裝置旋轉）時，既有劃線的百分比座標基準會不一致，導致高亮筆劃拉伸或錯位；`pageIndex` 欄位已經區分頁碼，換算時務必確認取用的是該頁自身的邊界框，不是雙頁合併後的邊界框。
- 劃線/備註的持久化（`Highlight`／`Note`／`Bookmark` 資料模型，含 `pdfPageIndex` 定位）不需要 schema 遷移。
- 若日後書籍實際存在可抽取文字層，可選擇性利用文字定位取得更精準的自動吸附選取範圍（例如選取矩形自動貼齊文字邊界）——列為錦上添花的可能優化方向，非本 Epic 的必要驗收條件，不影響前述保留矩形選取作為主要機制的決策。

### 書籤

- 新增書籤 toggle（星號圖示）：比對目前頁碼與既有書籤清單，行為比照 EPUB 既有的書籤 toggle 邏輯（有則移除、無則新增），資料模型使用既有的 `pdfPageIndex` 欄位，不需要新的資料層設計。

### E-Ink 影像濾鏡/裁切（FR-11 功能對等）

- 對比度/亮度濾鏡、型態學膨脹加粗（PDF 加粗）、智慧自動裁切、手動選區裁切，四項現行由原生端直接操作點陣圖完成的影像處理，改在 Dart 端對 `pdfrx` 輸出的頁面點陣圖資料重新實作，達到功能與可用效能對等（同樣的濾鏡參數範圍、同樣的裁切互動方式），不接受功能退化。
- 影像處理運算（尤其型態學膨脹屬於逐像素運算）一律於背景 Isolate 執行，不佔用 UI 主執行緒，避免翻頁/介面操作卡頓（呼應 User Story 16）。若背景 Isolate 效能仍無法達成功能對等的可用效能，保留封裝原生（C/C++ FFI）影像處理模組作為備案——`pdfrx` 本身已引入 PDFium 原生函式庫，技術上已有 FFI 邊界可供擴充，非新增另一套獨立機制。
- 對比度/亮度等濾鏡參數若由使用者拖曳 Slider 連續調整，須加上防手震延遲（debounce）或可取消的運算排程，避免拖曳過程中連續派送大量背景 Isolate 運算工作造成佇列塞車、UI 反應遲鈍（`/superpowers:receiving-code-review` 審查回應），具體防手震延遲時間與是否需要低成本即時預覽留給實作階段依真機體感調整。
- 智慧自動裁切維持現行「取樣偵測邊界後全書統一套用同一比例」的既有語意（非逐頁各自計算）；手動選區裁切維持「使用者框選矩形後全書統一套用」的既有語意。

### 檔案存取（`content://` URI 相容性）

- PDF 開書優先評估透過 `pdfrx` 的自訂讀取來源能力，橋接既有的系統檔案存取機制（沿用現行已用於原生 `PdfRenderer` 的檔案描述符存取方式）直接讀取，不需要真實檔案系統路徑、也不需要把檔案整包複製到 App 私有目錄——維持既有「不複製、直接引用原始檔案」的架構原則（避免大型 PDF 匯入造成雙倍儲存空間佔用，呼應 User Story 22）。
- 只有在前述橋接方式證實不可行（例如原生函式庫的非同步呼叫與既有平台頻道讀取機制無法順利介接）時，才退回「落地複製到本機快取」，且僅限於這個回退情境下使用，不做為預設路徑。

### 閱讀工具列（FAB 化，原 `epic-23-pdf-fab-toolbar` 併入）

- PDF 頂部工具列（現行傳統 `AppBar`，含系統預設返回箭頭 + 版面設定/筆記兩個按鈕）改為浮動圓形按鈕（FAB），視覺與位置比照 EPUB 既有樣式，重用既有的、跟隨 `Theme.of(context)` 且已考慮電子紙硬體對比的按鈕底色/圖示色邏輯。
- PDF 最終達到與 EPUB 相同的 6 顆 FAB 按鈕：返回／目錄／版面設定／書籤 toggle／筆記／進度-跳頁——原 `epic-23` 因目錄技術可行性未知而排除的第 6 顆按鈕，這次因為 `pdfrx` 內建大綱解析能力而可以真的加上。
- 沉浸模式（介面收合/展開）行為與 EPUB 既有機制一致。
- 現行 PDF 頂部工具列對應的原生 method channel 契約與其 Dart 端 `AppBar` 相關程式碼隨引擎替換一併退場。

### 新增依賴與建置影響

- 新增 `pdfrx` 套件依賴（內含 PDFium 原生函式庫，透過 `dart:ffi` 呼叫）。
- 需評估對 APK 體積、既有 Android 建置流程（Gradle 設定）、既有 `minSdk 24` 相容性的實際影響，作為實作階段的驗證項目（非本文件預先承諾具體數字）。

## Testing Decisions

- **主要測試策略：直接用 `flutter test`（非 `integration_test/`）對真實 PDF fixture 檔案驗證行為**——`pdfrx` 是純 Dart FFI，不經過 `PlatformView`，桌面 host（本專案開發/CI 環境）也能載入真實 PDFium 原生函式庫，不像現行架構的原生渲染只能在真機/模擬器上驗證（CLAUDE.md 既有「兩層測試架構」）。這代表新 PDF 閱讀 widget 的開書、頁數、目錄解析、搜尋、雙頁配對等行為，可以直接在一般 widget test 層級對真實檔案斷言，不必依賴真機。
- 現行 `app/test/fixtures/sample.pdf` 只有 345 bytes、無大綱、內容過於單薄，不足以驗證目錄解析、多頁跳轉、雙頁配對等新行為——需要新增一份內容更豐富的 PDF fixture（多頁、含大綱/書籤樹），提交進版控供測試使用，比照既有 `sample.epub`／`sample_fixed_layout.epub` 的既有慣例。
- 何謂好測試：只驗證外部可觀察行為（頁數、目錄項目內容、跳轉後的目前頁碼、搜尋結果數量與位置），不斷言 `pdfrx` 內部實作細節。
- E-Ink 影像濾鏡（對比度/亮度/加粗/裁切）的像素級輸出驗證，因涉及視覺結果比對，優先以既有專案慣例（例如像素取樣斷言、已知輸入輸出配對）覆蓋核心邏輯，真機視覺確認仍為建議（非強制）的收尾步驟，比照既有 Epic 的既有慣例（例如 Epic 22 的「真機視覺確認」建議步驟）。
- `integration_test/` 仍保留給真正需要真機/模擬器才能驗證的情境（例如與原生系統互動的部分，若實作後發現仍有這類殘留依賴）；預期本 Epic 完成後 PDF 相關 `integration_test/` 案例數量會明顯減少，非增加。
- 既有 `ReaderScreen` 層級的 widget test（`FoliateEpubReaderView`／PDF 共用的 `_state` 狀態機、FAB 按鈕、Bottom Sheet 行為等既有測試慣例）延伸涵蓋新 PDF widget，測試撰寫方式比照既有 EPUB FAB 相關測試的既有模式（直接呼叫 widget 暴露的回呼模擬狀態變化，而非嘗試模擬底層原生事件）。

## Out of Scope

- 手寫/自由繪圖標註（stylus 壓力感測、向量筆畫直接畫在頁面上）——與既有文字選取劃線系統是完全不同的互動模式，另立獨立後續 Epic 評估。
- 全書庫全文檢索（FTS5）——既有 Backlog 項目，與本次「單一文件內搜尋」是不同功能，不整合。
- EPUB 任何既有行為變更——本 Epic 純粹是 PDF 這一側的引擎替換與功能補齊。
- iOS 實作——`epic-13-ios` 仍是最低優先順序，`pdfrx` 的 iOS 相容性是附帶效益，非本次驗收範圍。
- 技術 Spike——經確認不先做真機驗證 Spike，直接進入實作，技術風險於實作/真機驗證階段處理（見 `design.md` 決策 5、ADR 0022）。
- PDF 內容編輯（文字/圖片修改）——PRD 既有明確排除範圍，不因引擎替換而重新評估。

## Further Notes

- 本 Epic 是專案至今最大規模的單一格式渲染路徑重寫，實作階段建議拆解為足夠細的垂直切片工單（`issues.md`，Scrum Master 階段），讓每張工單本身可獨立驗證、不必等全部功能到齊才能看到進度——例如「引擎替換＋既有功能對等（開書/頁數/雙頁/書籤/劃線/影像濾鏡）」可作為優先於「新增能力（目錄/搜尋/縮圖）」的第一批工單，確保任何時間點退回現行架構的成本可控。
- `content://` URI 橋接方式（`openCustom` 或退回落地複製）、新 PDF fixture 的具體內容設計、頁碼縮圖的快取策略，皆留給實作階段第一個相關工單的 `plans/plan-issue-N.md` 具體決定並附上驗證證據，本文件僅定義方向與應維持的既有原則（不落地複製、功能對等）。
