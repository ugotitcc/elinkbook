2026-09-10 人類新增需求：「啟用全文檢索」拆成「PDF」與「非 PDF（Foliate）」兩個獨立開關，並要求分析理由。分析結論（已寫入 `design.md`/`CONTEXT.md`）：使用者原始假設「PDF 較吃資源」查證後方向相反——PDF 走純 Dart/FFI（`pdfrx`），資源成本相對輕，真正吃資源的是 Foliate 格式的 Headless WebView；但「PDF 索引效果可能不佳」是站得住的理由——掃描/圖片型 PDF 常無真正文字層，且不像 CBZ 能在格式層級提前偵測，逐檔案判斷成本高，讓使用者自行整體關閉 PDF 索引是務實做法；Foliate 格式則反過來是「資源疑慮」成立、「效果疑慮」低，兩者關切點互補，故拆成兩個獨立開關（`ContentIndexCategory { pdf, foliate }`）皆合理。已連動修訂 `design.md` 決策 3（拆分理由＋兩組獨立進度顯示＋各自獨立確認 Dialog 文案）、`spec.md` §4（`FullTextSearchSettingsRepository.isEnabled/setEnabled(category, ...)`，排程器本身不需感知分類、篩選責任在插入 pending 列這一步）／§3.3／§5／§7、`CONTEXT.md`「啟用全文檢索」詞條。**連帶影響既有依賴圖**：`spec.md` §7 下載完成事件現在需要查詢分類是否啟用才決定要不要插入 pending 列，Issue 2（CBZ/DRM/下載邊界處理）因此改為依賴 Issue 3（`FullTextSearchSettingsRepository`），原提案「Issue 2 與 Issue 3 可平行」不再成立，`issues.md` 依賴圖與 Issue 2/3/4 內容已同步修訂。下一步：實作者依 Issue 0 開始 TDD 循環（撰寫 `plans/plan-issue-0.md` 並發起審查）。

2026-09-10 雙開關修訂後的 `spec.md` 再次審查（`reviews/review-spec.md`，🟡 Changes Requested，1 Important／1 Minor）：(1) I-1 用 WebFetch/WebSearch 查證多個獨立來源（`sqlite.org` 官方文件、Simon Willison TIL）確認屬實——`COUNT(*) FILTER (WHERE ...)` 是 SQLite 3.30.0 才加入的語法，Android 11 系統 SQLite 3.28.0 不支援，會拋語法錯誤；已改寫為所有版本通用的 `COUNT(CASE WHEN ...
