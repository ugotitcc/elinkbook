第 1 節

現行 UI 架構

App 外殼
main.dart 手動建構所有 repository、client 與服務，再把約 30 個依賴一次交給 ElinkBookApp，最後只渲染一個 MaterialApp，home: LibraryScreen。沒有路由表、沒有 router 套件、沒有 deep link、沒有 navigation observer。
導覽模型
100% 是在 widget callback 裡直接 Navigator.push(MaterialPageRoute(...))，每個目的地都在呼叫點就地建構、就地填入完整依賴清單；返回後靠零散的 .then((_) => reload()) 重新載入。
狀態管理
全面 setState，加上兩個 ChangeNotifier（LibraryBookListController、TtsController）。沒有全域 store；主題與 E-Ink 模式是從 _ElinkBookAppState 以 callback 一層層往下傳。

目前的導覽結構

LibraryScreen（唯一的根畫面） ├─ LibraryScreen(groupFilter: "…") ← 進入分類 = 在堆疊上「再推一個書架」 ├─ ReaderScreen ← 全螢幕；EPUB/KF8/CBZ/TXT/MD（foliate-js + InAppWebView）＋ PDF（pdfrx） │ ├─ 目錄 Sheet ├─ 筆記 Sheet（2 分頁） ├─ 版面設定 Sheet（4 分頁） │ ├─ FXL 設定 Sheet ├─ PDF 設定 Sheet ├─ PDF 縮圖面板 │ ├─ PDF 搜尋面板 ├─ 備註編輯對話框 ├─ 版面預設命名對話框 │ └─ 版面預設套用書籍選擇畫面 ├─ CloudBrowserScreen（Google Drive） ← 由「＋」彈出選單進入 ├─ CloudBrowserScreen（OneDrive） ← 由「＋」彈出選單進入 ├─ RemoteServerListScreen ← 由另一顆雲朵圖示進入 │ ├─ RemoteServerFormScreen │ └─ RemoteCatalogScreen → RemoteCatalogScreen → …（每下鑽一層分類推一個新畫面） └─ SettingsScreen ├─ 字型管理 ├─ 閱讀預設值 ├─ 導航熱區 ├─ 同步 ├─ 雲端匯入帳戶 ├─ 閱讀器 Console Log └─ 關於
依賴靠 prop 一層層硬傳
LibraryScreen 收下四組依賴包，純粹只為了轉交給 ReaderScreen 與 SettingsScreen；SettingsScreen 收 11 個參數，其中 6 個只是再轉交一次。
可為 null 的依賴被當成功能開關
依賴為 null 時 UI 靜默停用該項目。檔案內註解已記錄過一個 Critical bug：漏傳 callback 導致 E-Ink 開關「看得到、按了沒反應」。
閱讀器是一個巨型 widget
ReaderScreen 3,048 行、單一 State 類別，同時承擔兩套渲染引擎、TTS、劃線備註、書籤、目錄、PDF 裁切、PDF 搜尋、同步 checkpoint 與沉浸模式。
第 2 節

現行設計系統

目前只有「色彩系統」，其餘皆無。theme/app_theme_data.dart 依照 prototype/index.html 的 CSS 變數手工建了四套 ThemeData（淺色／深色／羊皮紙，加上 E-Ink 強制覆蓋）。字級、間距、圓角、陰影、動態與密度完全沒有被建模。

實際有定義的色彩角色

角色淺色深色羊皮紙E-Ink
背景 scaffold#F8F8FA#121214#F4ECD8#FFFFFF
surface／card#FFFFFF#1E1E22#FAF3E3#FFFFFF
onSurface#1A1A2E#E8E8EC#5B4636#000000
outline／分隔線#E0E0E5#86868F#E6DCBF#000000
primary#8B5CF6#BB86FC#B45309#000000
其餘所有角色未設定 → 由 Flutter M3 預設調色盤自動補上 secondary、tertiary、error、所有 container 與所有 -Variant
做得好的地方
  • 深色主題的 outline 與 Switch 軌道色，是依真機電子紙硬體實測反覆調整的，且把感知亮度差的推導完整寫在註解裡。
  • E-Ink 主題停用 splash／hover／highlight，方向完全正確。
  • 書架格子的頁尾高度由 MediaQuery.textScalerOf 推算，系統放大字級時不會被裁切。
  • 主題與 E-Ink 偏好在 runApp 之前載入，開機不閃白屏。
缺少的部分
  • 沒有 TextTheme。所有字級都是字面值：10、12、13、16，還有各檔各自的 _appBarTitleFontSize = 13。
  • 沒有間距尺標。SizedBox／EdgeInsets 的 2、4、6、8、12、16 都是各呼叫點自行決定。
  • 沒有圓角與陰影 token。選項是 8、封面徽章是 12、TTS 控制列是 28、elevation: 4 只出現一次。
  • 沒有動態與密度 token，因此 E-Ink 無法被表達成一個「修飾子」。
  • 寫死的非主題色（Colors.grey.shade200/300、black45、black54、Colors.white）散落在封面、徽章與清單列。

第 4 節

問題發現

依介面分組，涵蓋「UI 不一致」與「UX 問題」。P0 會阻斷或破壞核心任務、P1 明顯消耗使用者時間與信任、P2 為精緻化。

A · 導覽與資訊架構

P1「堆疊一層書架」不等於資料夾
進入分類會推一個全新的 LibraryScreen。沒有麵包屑、AppBar 標題不顯示分類名稱、排序／檢視／匯入按鈕全部重複出現，返回只能賭返回鍵。使用者無法判斷自己是在「篩選」還是在「另一個地方」。
library_screen.dart · _openGroupFilteredView、groupFilter
P1「把書弄進來」有四道門、分散在三個位置
本機檔案、資料夾、Google Drive、OneDrive 在同一個「＋」選單；OPDS 在隔兩格的雲朵圖示；雲端「帳戶」則在設定裡。四種瀏覽器、四套選取與確認流程，目標卻只有一個。
library_screen.dart · library_import_button、library_remote_library_button／cloud_browser_screen.dart／remote_catalog_screen.dart
P2沒有路由表，就沒有 deep link 與狀態還原
所有目的地都是就地建構。從通知「繼續閱讀」、Android 桌面捷徑直接開某本書、行程被系統回收後還原閱讀器，都需要一層目前不存在的路由。

B · 主題、色彩與深色模式

P0寫死的灰與黑，穿透了每一個主題
空白封面用 Colors.grey.shade300、分類拼貼空格用 shade200、選取勾選與「未下載」徽章用 black45／black54 配白色圖示、格狀進度文字用 Colors.grey。在深色模式下，這些是近黑書架上的亮斑；在 E-Ink 模式下，它們正是那個「承諾純黑白」的模式最無法乾淨呈現的中間灰。
book_cover.dart · library_screen.dart _GroupGridTile、_GroupListTile、_BookGridTile
P0只定義 5 個角色，約 25 個由 Material 預設補齊
每個 ColorScheme 只給 primary、surface、onSurface、outline。Material 實際拿去畫的 primaryContainer、onSurfaceVariant、secondary、error、各種 surfaceContainer* 全部回退到 M3 baseline。羊皮紙主題最慘：一張溫暖的米色書頁，選中的晶片、對話框、SnackBar、Switch 卻是原廠淡紫。而 ReaderOptionTile 的「選中樣式」正好就吃這兩個沒被定義的角色。
app_theme_data.dart _buildSepiaTheme／widgets/reader_option_tile.dart
P1E-Ink 模式是用「比對兩個顏色」猜出來的
ReaderOptionTile 用 primary == Colors.black && scaffoldBackgroundColor == Colors.white 判斷自己在 E-Ink。未來任何純黑白／高對比主題都會被誤判，而且其他 widget 根本無從詢問這個問題——所以整個 App 只有一個元件做了 E-Ink 適配。
P2主題是全域的，但「閱讀頁面」本質上是分離的
淺色／深色／羊皮紙同時改變 App 介面與書頁。多數讀者想要的是「深色介面 ＋ 羊皮紙書頁」，或「書頁跟隨環境光、書架維持不變」。目前沒有把「App chrome 主題」與「閱讀頁主題」分開。

C · 字級與間距

P1書名 12px、進度 10px 灰字
在使用者看最久的書架上，書名是寫死的 fontSize: 12 且限制單行，進度是 fontSize: 10 的未定義灰。對一個以正體中文為核心、讀者年齡層偏成熟的閱讀器來說，這低於舒適閱讀尺寸，而且單行會截斷大多數中文書名。
P1沒有字級層級，所以到處都沒有階層
設定列、Sheet 內的區段標籤（「欄數」「上邊界」）、對話框標題、清單副標，全都用 Material 預設字級與字重，長選項面板讀起來就是一整欄毫無區分的控制項。版面設定 Sheet 有四個分頁的滑桿，分頁內完全沒有視覺分組。
P2臨機間距造成看得見的節奏斷裂
格狀 padding 8、橫向間距 8、縱向 12；Sheet padding (16,12,16,16)；頁尾 (16,8)；2/4/6/8/12 各處自訂。單看都沒錯，合起來就是沒有格線。

D · 按鈕、卡片、對話框與 Bottom Sheet

P1四種互不相干的「單選」語彙
版面 Sheet 用自訂描邊晶片 ReaderOptionTile；字型用裸 DropdownButton；排序用 PopupMenuButton 並以粗體＋主色標示目前值；布林用 SwitchListTile。四種「選一個」的表達方式，出現在相鄰的兩個介面裡。
P1破壞性操作的確認標準不一致
批次刪除會確認；「移除本機快取」「強制 FXL」「恢復自動判斷」則從純圖示按鈕立即執行、立刻退出選取模式、沒有復原。而且後兩者在書架上完全看不出結果，使用者無法確認自己到底有沒有按到。
library_screen.dart · _buildSelectionAppBar 等
P2沒有共用的 Sheet 外殼
目錄、筆記、版面設定、FXL 設定、PDF 設定與兩個跳頁 Sheet 各自建容器，因此拖曳把手、標題、關閉方式、最大高度與安全區 padding 都不一樣。

E · 圖書庫／書架

P0匯入失敗被靜默吞掉
兩條匯入路徑都用 catch (_) { } 包住，註解說明用意是保護 widget 樹。但使用者看到的結果是：檔案損毀、權限不足、無法解壓——通通長得跟「什麼都沒發生」一模一樣。而且成功提示在「匯入 0 本」時也被抑制，所以整批不支援的檔案是完全無聲的。
library_screen.dart · _pickAndImportFiles、_pickAndImportFolder、_showImportResultSnackBar
P0沒有任何方式可以「找一本書」
沒有搜尋框、沒有書名／作者篩選、沒有注音或 A–Z 索引、沒有「最近閱讀」列。唯一的收斂工具是四種排序與手動分類。書量到幾十本就變成線性掃描，到幾百本就無法使用。全文檢索是已知的路線圖項目，但目前連「詮釋資料篩選」都沒有。
P1歸類後的書會從頂層書架消失
為了避免重複顯示，頂層書架只顯示分類拼貼格＋未分類書籍。使用者一旦把書歸類，它就從主畫面消失，包含正在讀的書。而且 2×2 拼貼格外型跟一本書幾乎一樣，書架上變成兩種同輪廓的物件，只能靠標題括號裡的數字分辨。
P1書架 AppBar 上有六個彼此競爭的動作
排序、檢視切換、匯入、管理分類、遠端書庫、設定——全是純圖示、全是同等權重，其中「匯入」還是本畫面的主要動作。檔案內已有一段關於工具列溢位修復的註解，正是這個壓力造成的。匯入應該是 FAB，而不是跟診斷性質的齒輪並列。
P2空狀態過於單薄
只有「尚未匯入書籍」加一顆按鈕。首次啟動正是說明「四種匯入方式」與「支援哪些格式」的最佳時機。

F · EPUB／PDF 閱讀器

P0右側的「浮動按鈕塔」
閱讀器介面是七顆手動定位的 ClipOval 圓形按鈕：返回在左上，目錄／設定／書籤／筆記／跳頁／朗讀沿右緣堆在 top: 16, 72, 128, 184, 240, 296。在手機上那是一條約 344dp 的不透明長柱壓在內文上——而這個 App 的核心差異化正是「正確的中文直排」，右側恰恰是直排書頁的起始邊。更嚴重的是，這整組按鈕被寫了兩次：foliate 一份、PDF 一份，幾乎完全重複。
reader_screen.dart · _buildBody，約 2190–2450 行
P020dp 高的 AppBar 搭配 18px 圖示
殘存的 AppBar 路徑設定 toolbarHeight: 20、iconSize: 18、標題 13px，並強制 shrinkWrap 觸控區——不到 48dp 最小值的一半，而且是在單手操作、電子紙觸控精度更差的裝置上。檔案註解自己也承認結果「偏擠」。
P1兩套介面系統並存，其中一套幾乎已是死碼
Scaffold AppBar 對流式 foliate、FXL 與 PDF 一律被抑制——也就是對幾乎所有真實書籍都不生效——實際工作由浮動按鈕塔承擔。但那條死分支仍保有自己的標題 widget、「點章節名開目錄」行為與 action 清單，而浮動塔刻意不重現這些。同一組介面存在兩份互相偏離的定義，是長期的回歸風險。
P1選取工具列用「估計尺寸」定位
_annotationToolbarHeight = 104／Width = 256 註解明說是估計值，卻被用來把工具列箝制在畫面內。日後多一個劃線顏色、刪除按鈕文案變長、或使用者放大系統字級，工具列就會被推出畫面或蓋住選取內容。
P1開書時只有一個轉圈圈疊在純色上
一層全幅底色遮罩加置中的 CircularProgressIndicator 蓋住原生視圖直到首次繪製。在 App 最長的一段等待中，畫面上完全沒有書的身分（封面、書名、上次位置）；而無限旋轉的轉圈圈，是電子紙上最糟糕的載入表現方式。
P2直排介面是把橫排整個轉 90 度
直排模式的頁眉與進度文字，是把橫排 widget 放進 RotatedBox(quarterTurns: 1)。能動，但截斷、對齊與觸控區都在錯誤的軸向上被推理——而且按鈕塔並不會跟著轉。

G · TTS 朗讀

P0關閉控制列＝弄丟 App 內唯一的停止鍵
✕ 只收合控制列、不暫停朗讀（這是刻意設計並寫在註解裡，tooltip 也寫「關閉朗讀控制列」）。使用者以為在關掉浮層，結果是聲音繼續播、畫面上再也沒有控制項；只能回到按鈕塔的朗讀鍵或系統通知救援。「關閉但不停止」必須配一個常駐的「正在朗讀」提示，而不是把它藏起來。
P1語速是「塞在圖示按鈕裡的文字」，而且盲目輪播
1.00x 被當成 IconButton 的 icon 渲染，點一下跳到下一個預設值，沒有清單、沒有範圍、要退回只能整圈轉完。使用者看不到有哪些選項，也無法直接跳到想要的值。
P1跟讀朗讀在 UI 上沒有任何「狀態」
五顆傳輸鍵，就這樣：沒有目前句子、沒有章節、沒有章內進度、沒有語音選擇、沒有睡眠定時、沒有引擎資訊。底層的 CFI 段落同步做得很紮實，卻只呈現為頁面上的高亮。
P2CBZ 顯示一個永遠停用的播放器
漫畫會拿到一顆灰掉的播放鍵加解釋用的 tooltip。tooltip 以滑鼠 hover 為前提，觸控裝置幾乎不會被發現；純圖像格式應該直接不提供這個入口。

H · 筆記與劃線

P1書籤與筆記的圖示語言互相矛盾
加書籤用星星；而包含書籤／劃線／備註的筆記 Sheet，入口卻是 Icons.bookmarks、標籤寫「筆記」。也就是：書籤動作是星星，書籤圖示打開的是筆記。進到 Sheet 裡，兩個分頁又用 🔖／✏️ emoji，是第三套圖示語言。
P1兩列、最多 8 顆按鈕的工具列蓋在剛選取的字上
第一列三色＋底線＋關閉，第二列複製／備註／刪除，固定 256×104 的方塊錨在選取矩形旁。在手機上大約是頁寬的三分之一、頁高的八分之一，而且不論選取範圍留下多少空間，版面都不變。
P2劃線備註只存在於單本書內
只能從書內開啟。沒有全書庫的「所有劃線」檢視、沒有跨書搜尋，Markdown 匯出也是單本——這其實低估了資料層已經支援的能力。

I · OPDS、雲端來源與同步

P1每下鑽一層 OPDS 分類就推一個畫面
在 Calibre 書庫往下四層，堆疊上就留了四個完整畫面，各自帶著自己的 client 實例、選取集合與分頁狀態。沒有麵包屑，回到目錄根只能連按返回。
P1雲端與 OPDS 沒有共用的瀏覽模式
兩個獨立畫面在做同一件事：認證、列出、選取、查重、排下載佇列、顯示進度、行動數據警告——卻是各自實作。再加一個 WebDAV，就是第三份。
P2同步在出事之前完全隱形
PocketBase 引擎在 App 進背景與各 checkpoint 執行，UI 只有一個設定畫面加一個「位置衝突」對話框。書架上沒有同步狀態、沒有最後同步時間，也沒有靠近內容的「立即同步」。

J · 設定

P1八列扁平清單，沒有任何分組
外觀、閱讀預設、手勢、同步、雲端帳戶、診斷、關於全擠在同一個 ListView，沒有區段標題、沒有圖示、沒有說明文字。「導航熱區」與「閱讀預設值」光看標題根本猜不到內容。
P1閱讀偏好散落在三個地方
全域預設在「設定 → 閱讀預設值」、單書覆寫在閱讀器 Sheet、具名版面預設在該 Sheet 的第四分頁。「覆寫 ?? 自動偵測 ?? 全域」這個解析順序在程式裡實作得很正確，但 UI 從未說明；於是「拉了滑桿卻沒反應（因為存在單書覆寫）」與「這是 bug」在使用者眼中無法區分。「顯示頁首／頁尾」等常用開關也被埋在「邊界首尾」分頁的四個邊界滑桿之後，閱讀器內沒有快速入口，等於功能存在但發現不了。
P2開發診斷功能出現在使用者選單裡
「閱讀器 Console Log」與其攔截開關夾在同步與關於之間，應該收進「關於」畫面連點版號後才顯示的除錯區。

K · 手機／平板響應式

P1只看方向、從不看寬度
書架直向 3 欄、橫向 4 欄——7 吋電子書、13 吋平板、摺疊機一視同仁。大平板上就是超巨大的封面配一整螢幕的說明文字。沒有斷點、沒有 NavigationRail、沒有雙欄主從版面，設定畫面也沒有最大內容寬度。
P2閱讀器介面錨在絕對像素座標上
按鈕塔的 16/72/128/184/240/296 與工具列的 256×104，都是為手機挑的 dp 值。平板上會擠在角落；小尺寸電子書橫向時，按鈕塔會超出畫面底部。

L · 電子紙（E-Ink）裝置可用性

P0E-Ink 模式下的主要控制項竟是滑桿與轉圈圈
字級、字重、行距、段距、字距、四邊邊界、欄寬與跳頁全部是 Slider；載入是 CircularProgressIndicator。兩者都是連續動態元件：拖一次滑桿會觸發數十次局部刷新與嚴重殘影，而轉圈圈永遠不會靜止。E-Ink 模式關掉了 splash 與水波紋，卻放過了最傷的兩個。
P1E-Ink 適配只存在於兩個地方
這個旗標只到達 RemoteCatalogScreen（把無限捲動換成離散換頁，做法完全正確）與 ReaderOptionTile（靠比色猜出來）。書架仍是連續捲動、頁面轉場仍有動畫、Bottom Sheet 仍會滑入，也沒有任何畫面提供離散換頁。正確的直覺，只落實在十六分之一的畫面上。
P1純黑白模式裡仍殘留中間灰
E-Ink 主題本身嚴格黑白，但寫死的 grey.shade200/300 佔位、black45 徽章與灰色進度文字完全繞過它——正是這個模式存在的目的所要消除的抖動中間調。
P2沒有手動全刷，也沒有實體鍵提示
音量鍵翻頁已在平台通道接好、導航熱區也可設定，但 UI 從未告訴第一次使用電子書裝置的人這些功能存在；殘影累積時也沒有「手動全螢幕刷新」的手勢。
第 5 節

建議的設計系統

用一個 ThemeExtension——命名為 ElinkTokens——掛在每一份 ThemeData 上，讓 widget 永遠不再讀字面值，也讓 E-Ink 從「換一套主題」變成「套在現行主題上的修飾子」。

1 · 兩層色彩
把 chrome（書架、設定、Sheet）與 page（閱讀頁）分開。淺色／深色／羊皮紙各自填滿完整 M3 ColorScheme，不留任何角色給 baseline。再加上 App 真正需要的語意色：highlightYellow/Green/Blue、underline、progressTrack、coverPlaceholder、badgeScrim。
2 · 字級層級
真正的 TextTheme，行高採 CJK 安全值（1.5–1.7），任何常駐標籤下限 14sp。書架書名 15sp／2 行、詮釋資料 13sp、區段標題 13sp 加字距、Sheet 標籤 15sp 半粗。全部尊重 textScaler——現有那段 scaler-aware 的頁尾高度計算，應該變成通則而不是特例。
3 · 間距與形狀
4dp 尺標，開放為 space.xs…xxl（4/8/12/16/24/32），圓角三階（8 / 16 / 28，對齊現有形狀），陰影只留兩階。另加 maxContentWidth，讓設定與表單在平板上不再無限拉寬。
4 · E-Ink 作為修飾子
tokens.isEink 加上 tokens.motion（full / reduced / none）與 tokens.paging（scroll / discrete），任何 widget 都能查詢。綁定到：零時長轉場、離散清單換頁、以 stepper 取代 slider、以確定式進度取代轉圈圈、邊框 ≥1.5dp。
5 · 密度與觸控目標
由共用按鈕元件強制 48dp 最小觸控目標，isEink 時提高到 56dp，並淘汰各處自行加的 shrinkWrap 覆寫。
6 · 圖示與語氣
一個概念一個圖示並寫成文件：書籤＝bookmark（不是星星）、劃線備註＝edit_note、目錄＝toc、來源＝cloud_download。分頁標籤不用 emoji。每個純圖示控制項都要有可見標籤或長按標籤，而不是只有 tooltip。
第 6 節

建議的元件層級

三層，放在 lib/ui/，並訂一條硬規則：畫面只負責組合，不負責樣式。畫面檔案裡出現字面色值、尺寸或 padding，即視為 code review 不通過。

第 1 層 · 基礎元件
吃 token，完全不懂業務
EBButton · EBIconButton · EBSegmented · EBStepper（取代 slider）· EBSwitchRow · EBListRow · EBSectionHeader · EBCard · EBTag · EBSheetShell · EBDialogShell · EBEmptyState · EBErrorState · EBLoading（骨架、確定式）· EBPagedList
第 2 層 · 領域元件
懂「書」，但不懂「畫面」
BookCoverTile · BookListRow · GroupTile · ProgressRing · SourceBadge · ReaderChromeBar · ReaderOverlayScrim · SelectionToolbar · TocList · AnnotationRow · BookmarkRow · TtsPlayer · TtsExpandedSheet · SourceBrowser（列出＋選取＋佇列）· DownloadQueueRow · SyncStatusChip
第 3 層 · 外殼
畫面所在的響應式框架
AdaptiveScaffold（底部列 → rail → rail＋詳細窗格）· SettingsScaffold（最大寬度、分區）· ReaderScaffold（統一掌管介面顯隱、沉浸模式、安全區，以及所有格式共用的唯一一份 chrome 定義）

沿著程式碼裡已經存在的接縫把 ReaderScreen 拆開：一個 ReaderShell 負責 chrome、沉浸模式、各 Sheet 與生命週期；格式控制器（FoliateReaderController、PdfReaderController）藏在同一個介面後，對外只暴露位置、目錄、選取、書籤狀態與 TTS 段落。重複的 EPUB／PDF 兩份 chrome 會塌縮成一份，而 CFI 處理、foliate bridge、同步 checkpoint、音訊焦點等業務邏輯原封不動搬過去即可。

第 9 節

後續應該怎麼做（白話版）

用最簡單的比喻說一次。

你的 App 就像一間藏書非常好、但沒有請過室內設計師的書店。書（功能）很齊全而且品質很高——直排排版、CFI 同步、朗讀、雲端同步都紮實。問題出在「裝潢」：每個房間是不同師傅、在不同時間、用不同油漆和不同尺寸的層板做的。所以走進去會覺得亂，不是因為東西不好，而是因為沒有一本共用的裝潢規格書。
第一步（1–2 週）
先寫「裝潢規格書」
也就是 ElinkTokens：顏色、字級、間距、圓角各只有一份定義。先不要改任何畫面長相，只是把散落各處的 Colors.grey、fontSize: 12 換成規格書上的名稱。

為什麼先做：深色模式、羊皮紙、E-Ink 的一堆毛病會在這一步一起消失，而且之後每一項改動都會變便宜。
第二步（2–3 週）
修三個「會讓人生氣」的地方
① 閱讀器右邊那排浮動圓鈕 → 改成上下兩條工具列。
② 匯入失敗要出聲音 → 不要再靜靜吞掉。
③ 書架加搜尋框。

為什麼：這三件事分別對應「讀不舒服」「以為壞掉」「找不到書」，是使用者最容易流失的三個點。
第三步（持續）
把重複的零件收成共用件
按鈕、清單列、Bottom Sheet 外殼、空狀態各做一個共用元件，之後新畫面用組的，不再重寫。

為什麼：現在 33 個介面只靠 3 個共用元件，這是所有不一致的根源。收好之後，新功能開發速度會明顯變快。
一句話原則
不要一次重做整個 App。先建立規格書（token），再用規格書修最痛的三個點，最後把零件收成共用件。業務邏輯（foliate、CFI、同步、TTS、OPDS）從頭到尾完全不用動——這是這份報告刻意的設計，因為那些正是你最不該冒險的部分。
我需要你回答的三件事，才能開始設計
  1. 主要目標裝置是手機，還是 Android 電子紙閱讀器？這一題會改變幾乎所有 P0 的答案（滑桿 vs 步進器、介面密度、捲動 vs 換頁）。
  2. 原則上可以接受「底部三個目的地（書架／來源／設定）」的架構嗎？不能的話我改用另一種收斂方式。
  3. WebDAV 真的在規劃中嗎？是的話，來源模型現在就要一次設計對。
回覆之後，我會先依現有程式碼像素級重建目前的畫面（不是憑印象畫），再把新設計疊上去做對照。
