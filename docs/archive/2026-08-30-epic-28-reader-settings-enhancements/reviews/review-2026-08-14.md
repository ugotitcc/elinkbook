## 1. 優點與亮點 (Strengths)

1. **JSON Blob 儲存方案的考量周詳**：
   選擇使用 `prefs_json` (TEXT 欄位) 可以避免未來 `BookReaderPrefs` 新增欄位時需要同步維護兩張表的 SQLite Migrations，大幅降低了後續功能維護的複雜度與漏改的風險。
2. **元件職責劃分清晰**：
   將 `ReaderSettingsSheet` 定位為「純展示 (Stateless/Presenter)」元件，不直接執行 Repository I/O。所有的資料持久化和跨書邏輯都交給 `ReaderScreen` 處理，有利於進行 Widget 測試與單元測試。
3. **Issue 範圍與界定準確**：
   明確將字距、Console Log 開關、版面預設集三項需求的適用範圍限定在流式 EPUB，並排除不通用的 PDF/FXL，有助於收斂實作複雜度。
4. **防禦性設計與容錯規劃完善 (複審新增)**：
   規格書針對 JSON 反序列化時的 Enum 容錯處理（`enumByNameOrNull`）、double 類型轉換防護（以 `as num` 處理 `int` 與 `double` 轉型），以及寫入目標前的欄位污染過濾（`reflowableEpubFields`）都做出了非常清晰與嚴格的防禦設計，避免了後續可能引發的 App 崩潰風險。
5. **使用者體驗細節細緻 (複審新增)**：
   考慮了預設集在覆蓋（Replace）時的排序穩定度，採用 `id ASC` 排序防止卡片位置突然移位；且在批次寫入效能上進行優化（SQLite 交易包裹），避免大書庫跨書套用時造成 UI 執行緒卡頓。

## 2. 問題與疑慮 (Issues)

### Critical (必須修正)

#### Issue 2.1：JSON 反序列化時的 Enum 類型向下相容性與 Crash 風險 `[已修訂 / Resolved]`
- **對應文件**：[`spec.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/spec.md#L43)
- **問題內容**：
  `BookReaderPrefs.fromMap` 在還原 Enum 型別時（例如 `textAlign` 等）若使用 `byName()`，遇到未知名稱會拋出 `ArgumentError`。在未來版本新增 Enum 值，或是舊版資料回退解析時，會導致 Crash。
- **影響**：App 載入版面預設集或開書時崩潰，導致核心功能失效。
- **複審更新**：
  **已修訂**。規格書中已明確採納此建議，要求將 `fromMap()` 內所有 enum 欄位的還原邏輯改為透過安全輔助函式 `enumByNameOrNull`，遇到未知值時回傳 `null`（降級為系統預設值）。此防禦措施非常妥當，亦可作為公用小工具供未來其它 JSON 序列化場景使用。

#### Issue 2.2：JSON 數值反序列化時的 double 與 int 類型轉換崩潰風險 `[已修訂 / Resolved]`
- **對應文件**：[`spec.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/spec.md#L45-L46)
- **問題內容**：
  `jsonDecode` 讀回整數值（如字距剛好為 `0`）時會是 `int`，若實作者直接寫成 `map['field'] as double?` 會觸發 `TypeError`（`int` is not a subtype of `double`）。
- **影響**：反序列化 Preset 時拋出 `TypeError` 導致 Crash。
- **複審更新**：
  **已修訂**。規格書已強制要求所有 `double` 欄位的反序列化都必須沿用既有慣例 `(map['field'] as num?)?.toDouble()` 進行轉換，避免 `jsonDecode` 的型別不確定性引發 Collapse。

### Important (應該修正)

#### Issue 2.3：大書庫跨書套用時的 SQLite 批次寫入效能瓶頸 `[已修訂 / Resolved]`
- **對應文件**：[`spec.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/spec.md#L83-L96)
- **問題內容**：
  跨書套用時，若逐一呼召 `BookReaderPrefsRepository.save()` 會發送數十次獨立的 SQLite 寫入交易，每次都會觸發 fsync 磁碟同步，產生嚴重 I/O 阻塞。
- **影響**：UI 執行緒將被阻塞數秒，產生明顯的畫面卡頓（ANR）。
- **複審更新**：
  **已修訂**。規格書中已為 `BookReaderPrefsRepository` 明確新增支援 SQLite 交易（Transaction）的批次寫入方法 `saveMultiple(List<String> bookIds, BookReaderPrefs prefs)`，藉此大幅提升跨書套用時的效能，消除卡頓風險。

#### Issue 2.4：大書庫時的書籍選擇器效能與 UX 卡頓 `[已修訂 / Resolved]`
- **對應文件**：[`spec.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/spec.md#L98-L104)
- **問題內容**：
  若書籍過多，撈出所有書籍並在 Dart 記憶體中做 `detectBookFormat` 和 `isFixedLayout` 篩選會耗費大量 CPU 時間，造成點擊選擇器時出現延遲。
- **影響**：大書庫用戶介面延遲、滑動卡頓。
- **複審更新**：
  **已修訂**：
  1. **資料庫層級過濾**：已採納，在 `LibraryRepository` 新增 `listReflowableEpubBooks({String? excludeBookId})` 函式，直接在 SQL 語句中過濾非流式 EPUB 書籍，大幅降低讀回記憶體的資料量。
  2. **UI分頁與搜尋（YAGNI）**：考量到專案書庫規模目標通常小於 1000 本，且資料庫過濾後結果集更小，加上 Flutter `ListView.builder` 的延遲渲染機制，目前實作複雜的分頁與關鍵字搜尋確實屬 YAGNI。此評估在現行規模下十分合理，未來若有需要可作為獨立功能另立 Issue 處理。

#### Issue 2.5：多 PR 合併時的 SQLite Migration 版本衝突 `[已修訂 / Resolved]`
- **對應文件**：[`spec.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/spec.md#L65-L73)
- **問題內容**：
  若將本 Epic 互有依賴的 Issue 拆分為兩個獨立的 Migration 版本號，在同一個 PR 合併或分支並行時，容易造成資料庫遷移歷史臃腫與 Rebase 衝突。
- **影響**：增加分支合併衝突的機率與維護負擔。
- **複審更新**：
  **已修訂**。規格書中已修改了原本「一律各自遞增一個版本號」的設定，明確劃分了「同一個 PR 中合併」與「分開獨立合併」的兩種升級版本號處理方案，提供了清晰的 Migration 合併指引。

### Minor (建議優化)

#### Issue 2.6：Preset 命名限制與重複命名的覆蓋 UX 遺漏 `[已修訂 / Resolved]`
- **對應文件**：[`spec.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/spec.md#L20-L21)
- **問題內容**：
  原設計未對 Preset 命名做長度限制、空字元處理及重複命名時的 UX 處理方式進行規範。
- **影響**：UI 跑版、重複命名造成使用者混淆、空名稱無法選取。
- **複審更新**：
  **已修訂**。規格書已在「命名驗證」中加入了：
  1. **去空白不為空**：限制儲存前一律 `trim()`，且長度不可為空。
  2. **長度限制**：設定最大長度上限 20 字元，防止 UI 跑版。
  3. **重複名稱處理**：允許同名，不強制進行「同名即覆蓋」的隱性邏輯，所有覆蓋均統一從「存滿 3 組時的覆蓋選擇入口」進行二次確認，防止使用者誤觸。

#### Issue 2.7：套用 Preset 到當前書籍時，Bottom Sheet 內部的狀態刷新 `[已修訂 / Resolved]`
- **對應文件**：[`spec.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/spec.md#L109-L110)
- **問題內容**：
  套用到當前書籍時，如果 Bottom Sheet 仍開啟，其內部草稿狀態若未隨外部 `prefs` 變更而刷新，會導致控制項依然呈現舊值。
- **影響**：使用者會誤以為設定套用失敗。
- **複審更新**：
  **已修訂**。規格書明定於套用成功後，呼叫端在 `_handlePrefsChanged` 中更新 State 後，透過 `ReaderSettingsSheet` 內部的 `didUpdateWidget` 機制同步刷新內部的草稿狀態，以維持畫面一致性。

#### Issue 2.8：PDF/FXL 欄位在 `prefs_json` 中的潛在資料污染與過濾機制 `[已修訂 / Resolved]`
- **對應文件**：[`spec.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/spec.md#L25)
- **問題內容**：
  來源書籍若曾經歷過人工版面覆蓋切換，可能殘留非 null 的 PDF/FXL 欄位，這會導致複製設定時，這些欄位被帶入並污染目標流式 EPUB 書籍的偏好設定。
- **影響**：造成難以排查的排版 Bug。
- **複審更新**：
  **已修訂**。規格書修正了原設計「假設欄位恆為 null」的漏洞，改為採用明確的允許清單過濾（Allow-list filter）。新增 `BookReaderPrefs.reflowableEpubFields()` 方法，在複製或另存預設集寫入 `LayoutPreset` 前，強制清除不相關欄位，從代碼結構上杜絕污染。

#### Issue 2.9：Console Log 關閉當下不清空紀錄與無筆數上限 `[已澄清 / Resolved]`
- **對應文件**：[`design.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/design.md#L28) / [`spec.md`](file:///U:/MyDeveloper/AI/elinkBook/docs/epics/epic-28-reader-settings-enhancements/spec.md#L137)
- **問題內容**：
  關閉開關時未清空紀錄，且文件未說明 `ReaderConsoleLog` 的總筆數上限與清除按鈕設計，可能造成資料庫 log 膨脹。
- **複審更新**：
  **已澄清**。經審查專家核實 `app/lib/reader/reader_console_log.dart` 與 `reader_console_log_screen.dart` 的具體實作，發現：
  1. `ReaderConsoleLog` 是純記憶體的 `ValueNotifier`，App 重啟即清空，**不落地寫入資料庫/SQLite**，因此無資料庫膨脹問題。
  2. 程式碼中已預設設有最大 `500` 筆上限的 FIFO 裁切邏輯。
  3. `ReaderConsoleLogScreen` 的 AppBar 上已具備「清空」按鈕。
  因此，原審查之「資料庫 Log 膨脹」等疑慮與現行實作不符，確認現況不需要做任何修改，本 Issue 予以撤銷/澄清。
