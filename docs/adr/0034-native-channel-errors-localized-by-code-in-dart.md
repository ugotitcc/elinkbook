# ADR 0034：原生層 MethodChannel 錯誤訊息不做跨端在地化，改由 Dart 端依錯誤代碼對應

## 狀態

已採納

## 背景

`epic-45-interface-i18n`（FR-49 多語系介面）Discovery 階段探查 `BookMetadataChannel.kt`／`MainActivity.kt` 發現，原生端透過 `MethodChannel` 回傳給 Dart 的 `PlatformException` 帶有硬編碼正體中文錯誤訊息（例如「找不到檔案或檔案已損毀」「複製檔案至本機儲存失敗」），但均搭配穩定的錯誤代碼（如 `extraction_failed`／`copy_failed`）。抽查 Dart 端多數既有呼叫點目前直接捨棄這個原生中文字串（吞掉、轉成空結果），但不排除少數路徑會把它原樣顯示給使用者。多語系介面的範圍已決定涵蓋「執行期動態錯誤訊息」（見 `design.md`），這個原生層邊界情況需要明確的技術路線。

## 決策

任何要顯示給使用者看的錯誤訊息，一律由 Dart 端依原生回傳的**錯誤代碼**對應到 `AppLocalizations` 字串；原生端的中文 `message` 字串視為診斷/日誌用途，不直接顯示給使用者，也不嘗試把目前 `Locale` 傳遞給原生層讓它回傳對應語言的訊息。

理由：Kotlin 原生層沒有 Flutter `Locale`／`AppLocalizations` 的概念，讓它感知目前介面語言需要新增一條跨端狀態同步機制（例如每次 channel 呼叫都夾帶 locale 參數、或原生層自行維護語言狀態），徒增複雜度；且現有程式碼已經證實大部分路徑本來就不顯示原生訊息本身（用錯誤代碼分支處理邏輯），這個決策只是把既有隱性慣例明文化。

## 後果

- 往後任何新增的原生 channel 錯誤路徑，若訊息要顯示給使用者，開發時必須確保有對應的穩定錯誤代碼可供 Dart 端對應翻譯字串，不能只靠原生端的 message 字串內容。
- 原生端的中文錯誤字串可以繼續維持中文撰寫（純粹是開發者除錯用途），不需要跟著這次多語系介面工作被翻譯。
- 若某個原生錯誤代碼目前沒有對應的 Dart 端使用者可見顯示（多數既有路徑皆是如此），維持現狀捨棄訊息即可，不強制為每個既有代碼都補一個使用者可見字串。

## 曾考慮的替代方案

- **把 `Locale` 當作參數傳給每個 MethodChannel 呼叫，原生端各自維護多語系字串資源（Android `strings.xml` 多語系機制）**：技術上可行（Android 原生就有成熟的多語系資源機制），但這代表同一組錯誤訊息要在 Dart（ARB）與原生（`strings.xml`）各自維護兩份，且原生層目前只有極少數訊息真正會顯示給使用者，投入成本與現有實際需求不成比例，予以排除。
