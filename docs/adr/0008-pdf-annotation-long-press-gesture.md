# ADR 0008：PDF 劃線/備註改用長按直接觸發框選手勢，不沿用既有裁切「顯式模式切換」慣例

## 狀態

已採納（`epic-6-annotations` Discovery，`docs/archive/2026-07-18-epic-6-annotations/design.md` 決策 #3）。

## 背景

`PdfReaderView.kt` 已有一個處理「使用者在 PDF 頁面上框選一個矩形區域」的既有先例——`epic-4-pdf-enhance` 的手動裁切功能（`CropOverlayView.kt`）：使用者必須先點擊一顆按鈕，明確進入一個獨立的全螢幕裁切編輯模式（`cropEditModeActive` 旗標），在該模式下框選矩形，最後按確認才離開。這是本專案目前唯一一個「在點陣圖 PDF 頁面上框選矩形」的既有互動模式。

`epic-6-annotations` 的劃線功能同樣需要在 PDF 頁面上框選一個矩形（因 `android.graphics.pdf.PdfRenderer` 純屬點陣圖渲染、無文字層可供選字，見 `design.md` 問題陳述）。若沿用裁切既有慣例，使用者必須先點一顆「進入劃線模式」的按鈕才能框選；EPUB 端的劃線則是原生 WebView 選字手勢（長按直接拖曳選取），不需要任何「進入模式」的前置步驟。

## 決策

PDF 劃線改採「長按頁面直接觸發拖曳框選手勢」，**不**沿用裁切功能「先按按鈕進入獨立模式」的既有慣例，理由是讓 EPUB／PDF 兩端劃線功能的心智模型一致（皆為「長按直接開始標記」），使用者不需要為 PDF 額外學習一個「先進入劃線模式」的步驟。矩形繪製的視覺元件本身沿用／延伸 `CropOverlayView.kt`，僅觸發時機不同。

已查證 `PdfReaderView.kt` 目前無任何既有長按手勢綁定，與現有互動（九宮格熱區單擊翻頁、裁切模式的顯式按鈕進入）不衝突。

## 後果

- `PdfReaderView.kt` 內會同時存在兩種「框選矩形」的觸發哲學：裁切＝顯式按鈕進入獨立模式；劃線＝長按直接觸發，兩者刻意不對稱。日後在此檔案新增第三種框選類需求時，須個別評估該套用哪一種模式，不能假設兩者已收斂成單一慣例。
- 長按觸發框選與既有手勢（九宮格單擊翻頁、雙頁模式縮放/平移）之間的手勢競技場（gesture arena）優先權，尚未實測，需在實作/真機驗證階段確認不會誤觸發或搶奪彼此的手勢辨識。
- 劃線框選中若使用者縮放或平移，直接取消目前選取（不即時重算矩形座標），見 `design.md` 決策 #15。

## 曾考慮的替代方案

- **沿用裁切的「顯式按鈕進入模式」慣例**：與既有 PDF 互動哲學一致、實作上可完全複用 `cropEditModeActive` 的狀態機模式，但會讓 EPUB／PDF 兩端劃線的操作心智模型不一致（EPUB 直接長按選字，PDF 卻要先找一顆按鈕進入模式），使用者體感上像是兩套不同功能，予以排除。
